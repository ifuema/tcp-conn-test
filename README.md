# tcp-conn-test

测一台机器 / 一条链路**到底能同时保持多少条 TCP 连接**的零依赖 C 工具，支持 Linux、macOS、Windows。

它和普通压测工具的区别只有一点：**定速、缓慢地建连**。「并发容量」和「每秒新建连接数（CPS）」是两个指标，但很容易被混在一起。安全组、LVS/SLB、`nf_conntrack`、网卡队列、运营商网关都可能对 CPS 单独限流。一上来就猛建连，撞到的往往是 CPS 天花板，测出来的「并发上限」会偏小一个数量级，拿去做容量规划只会误导人。

## 特性

- **单进程单线程、非阻塞 IO**：Linux 用 epoll，macOS/BSD 用 kqueue，Windows 用 select。只依赖 C 标准库，Linux/macOS 下可以撑到百万级连接。
- **两种模式**：`conn` 测并发容量，`cps` 阶梯加压测新建速率。两种模式都会给出结论和归因。
- **自动判定触顶**：存活数长时间不再净增长，就自动停止并输出报告，不用一直守着按 Ctrl-C。
- **能区分三种触顶形态**：SYN 被静默丢弃、会话表满后踢旧建新、NAT 空闲超时悄悄掉线。
- **失败归因**：fd 耗尽、端口耗尽、超时、拒绝、重置分别统计，并给出对应的修复动作。
- **服务端对拍**：服务端单独输出 `当前 / 峰值 / accept累计 / close累计`，用来核对「客户端以为连上了」是不是等于「服务端真的收到了」。

## 快速开始

### 1. 编译

```bash
make          # 产出 ./server 和 ./client
make clean
```

Windows 的编译方式见 [Windows](#windows)。

### 2. 准备两台机器

客户端和服务端**必须分开放在两台机器上**。放在同一台机器上时内存和 CPU 会互相抢，测出来的数字没有参考价值。

两台机器都先调优，再在**同一条命令里**提升 fd 上限后启动程序：

```bash
sudo ./tune.sh

# 被压测机：监听 32 个端口，扩大四元组空间
bash -c 'ulimit -n 1048576 && ./server -p 8000-8031'
```

> `ulimit` 只对当前 shell 和它的子进程生效，所以要和启动命令写在一起。`tune.sh` 里的 `ulimit` 只作用于脚本自己的 shell，对之后启动的程序无效。

### 3. 推荐流程：先测 CPS，再测并发

**第一步：测出链路能承受的建连速率。**

```bash
./client -s 10.0.0.2 -p 8000-8031 -m cps
```

报告最后会给出「稳定上限」，并直接打印下一步该用的命令，建连速率取稳定上限的 30%：

```
【下一步】测最大并发连接数时, 建连速率取稳定上限的 30% 最稳妥 ——
          太快会撞 CPS 限流而误判成容量不足, 太慢则耗时过长:
    ./client -s 10.0.0.2 -p 8000-8031 -c <目标连接数> -r 600 -T 5
```

**第二步：按这个速率测并发容量。** 目标值建议给到预期上限的 2 倍，让它自然撞墙：

```bash
bash -c 'ulimit -n 1048576 && ./client -s 10.0.0.2 -p 8000-8031 -c 1000000 -r 600'
```

客户端每秒打印一行进度，触顶后自动停止并输出完整报告。中途按 `Ctrl-C` 也会照常输出报告。如果不想先测 CPS，直接用 `-r 200` 这类保守速率也可以，只是耗时更长。

### 4. 跑完看什么

报告的最后三段就是结果：

- `结束原因`：是达到目标、触顶、撞到本机上限，还是用户中断
- `【结论】`：最大并发连接数，以及触顶的形态
- `【原因】`：瓶颈在哪，下一步怎么做

最后**拿服务端的 `累计 accept` 和 `close累计` 与客户端核对**，见[服务端对拍](#服务端对拍识别伪造的-finrst)。

## 为什么必须慢速建连

|      | 并发连接数（`-m conn`）      | 每秒新建连接数 CPS（`-m cps`）  |
| ---- | ------------------------ | ---------------------- |
| 含义   | 同时**保持**多少条连接           | 每秒**新建**多少条连接          |
| 决定因素 | 内存、fd 上限、四元组空间、会话表       | CPU、网卡队列、backlog、限流规则  |
| 典型瓶颈 | `ulimit -n`、内存、conntrack 表 | SYN 队列、`syncookies`、网关限流 |
| 数量级  | 十万 ~ 百万                 | 几千 ~ 几万 / 秒            |

建连太快时，短时间内大量 SYN 涌过去，SYN 队列溢出，触发 `syncookies`，或者网关和 conntrack 开始丢 SYN。这时看到的是「建连失败」，但这**不代表**服务端撑不住这么多并发。换成每秒 200 条慢慢建，同一台机器可能稳稳接住 100 万条连接，两者常常差 10 倍以上。

手动区分的方法：固定一个目标连接数（比如 10 万），逐步提高 `-r`（50 → 200 → 1000 → 5000），观察下面几个拐点：

- `失败` 从 0 开始变正
- 报告里的 `建连耗时 p99` 明显抬升
- 服务端的 `accept 失败` 变正

**出现拐点时的速率就是 CPS 上限；低速下能达到的最大并发，才是真正的并发容量。** `-m cps` 模式就是把这个过程自动化了。

> 本机回环（127.0.0.1）测试看不出 CPS 瓶颈：中间没有任何设备，也没有真实的队列压力。

## 读懂输出

### 客户端进度行

```
[    63.3s] 存活=2366  峰值=2461  握手=18  累计成功=5340  失败=0  超时=0  对端关闭=2974  速率=100/s
```

| 字段   | 含义                                          |
| ---- | ------------------------------------------- |
| 存活   | 当前处于 ESTABLISHED 的连接数                       |
| 峰值   | 存活数的历史最大值，**也就是「最大并发连接数」**                  |
| 握手   | 已经发出 SYN、握手还没完成的连接数。顶到 `-I` 上限，说明 SYN 没有回应   |
| 累计成功 | 全程建连成功的总数，包括后来被关闭的                          |
| 失败   | 建连失败的总数，包括下面的「超时」                            |
| 超时   | 因 `-T` 超时而失败的连接：SYN 发出后**没有收到任何响应**          |
| 对端关闭 | 已建立的连接被对端 FIN/RST 关闭的条数                     |
| 速率   | 当前建连速率。连续失败 5 次会自动降速（`-A` 关闭这个行为）            |

几个一眼就能看出问题的组合：

| 现象                              | 说明                                    |
| ------------------------------- | ------------------------------------- |
| `握手` 顶满，`超时` 持续增长              | SYN 被上游静默丢弃（[形态 A](#形态-asyn-静默丢弃)） |
| `失败=0`，`对端关闭` 跟着 `累计成功` 一起涨     | 踢旧建新（[形态 B](#形态-b踢旧建新)）              |
| `累计成功` 在涨，`存活` 却往下掉            | NAT 空闲超时在悄悄回收（[形态 C](#形态-c悄悄掉线)）       |

### 服务端进度行

```
[   26.9s] 当前=2   峰值=1500   accept累计=10547   close累计=10545   accept/s=2000   close/s=2000   rx=0.0MB   maxfd=1507
```

`当前`、`accept累计`、`close累计` 用来和客户端的 `存活`、`累计成功`、`对端关闭` 对拍。服务端退出（`Ctrl-C`）时会输出汇总：峰值并发、累计 accept / close、`accept 失败`、最大 fd。

服务端启动时会读取系统的 `somaxconn`。如果 listen backlog 被内核截断，会直接告警：

```
[警告] backlog 被内核截断为 128 (你请求了 65535)。大并发建连时 accept 队列会溢出,
       表现为客户端报「建连成功」但服务端并未收到。
```

### 并发模式报告

```
================ 测试报告 ================
...
历史峰值并发    : 1500
结束时仍存活    : 1500
对端主动关闭    : 0
建连超时        : 0  (SYN 发出后无任何响应)
心跳发送        : 617, 心跳发现失效: 0
建连耗时(ms)    : min=0.01 p50=0.06 p99=9.38 p999=11.96 max=12.22
------------------------------------------
结束原因        : 达到目标连接数并完成观察

【结论】最大并发连接数
  已达成目标 1500 条, 观察期内保持稳定 —— 尚未触顶, 可加大 -c 继续压

【原因】
  全程零失败, 未触及瓶颈。
```

如果有失败，报告里还会列出按 errno 分类的「错误分布」。

### CPS 模式报告

CPS 模式按档位逐级加压（默认 `200,500,1000,2000,4000,8000,16000`，每档 10 秒），每档结束打印一行，最后输出结论和原因。下面是一次撞到拐点的报告（节选）：

```
档位 目标/秒 实测/秒 达成率 成功/尝试   成功率 p50(ms)   p99(ms)   判定
1     1000      1000      100    % 3999/3999        100.0  % 0.13      1.4       PASS
2     4000      2753      77     % 12497/12507       99.9   % 388.76    1014.5    未达成

【结论】最大每秒新建连接数(CPS)
  稳定上限 : 1000 条/秒  (成功率 >= 95% 的最高档)
  临界值   : 目标 4000 条/秒时开始恶化

【原因】
  拐点档  : 4000 条/秒 —— 成功率仍有 99.9%, 但延迟已严重恶化
  佐证    : p99 延迟 1.4ms -> 1014.5ms (抬升 725 倍, 队列严重积压)
  该档错误分布:
      Connection reset by peer         12         100.0%
  判定    : 连接被立即重置 —— 本机或服务端 somaxconn 过小
```

每一档从四个维度判定，不只看成功率：

1. **达成率** = 实际发起速率 ÷ 目标速率。达成率低说明客户端自己发不出来，这一档作废。
2. **成功率** = 成功 ÷ (成功 + 失败)。分母不包括还在握手的连接。
3. **p99 延迟恶化倍数**：即使成功率是 100%，延迟涨了 10 倍以上也算拐点。
4. **握手窗口饱和度**：用来区分「客户端发不出」和「对端接不住，握手迟迟不返回」。

> 客户端是单线程的，在本机环境大约能发到每秒 3000 条。被测链路的 CPS 明显高于这个值时，工具会提示「速率未达成」。这时测到的是客户端自己的上限，需要多开几个进程并行加压。

## 诊断：数字上不去时

同样是「数字上不去」，背后可能是三种完全不同的机制。判读顺序：**先看 `失败` 和 `对端关闭` 哪个在涨。**

| 形态           | `失败`       | `对端关闭`        | `存活`       | 根因                 |
| ------------ | ---------- | ------------- | ---------- | ------------------ |
| A. 静默丢弃      | ≈ `超时`，持续涨 | 0             | 卡死不动       | 会话配额用满，新 SYN 被丢     |
| B. 踢旧建新      | 0          | 跟着 `累计成功` 涨   | 压在某个水位     | 会话表满，中间设备踢旧连接让位    |
| C. 悄悄掉线      | 0          | 0             | 缓慢下降       | NAT 空闲超时回收，靠心跳才能发现 |

### 形态 A：SYN 静默丢弃

```
[   138.2s] 存活=2004  峰值=2004  握手=6  累计成功=2004  失败=164  超时=164  对端关闭=0  速率=1/s
```

`存活` 卡死不动，`失败` 约等于 `超时` 并且持续增长，`对端关闭=0`，`握手` 顶到 `-I`。说明包根本没到达服务端就被丢掉了，但**已建立的连接全程没有掉线**，服务端没有主动断开任何一条。多见于链路上的 NAT/CGNAT 会话配额用满，排查方法见[链路瓶颈定位](#链路瓶颈定位)。

### 形态 B：踢旧建新

```
[    63.3s] 存活=2366  峰值=2461  握手=0  累计成功=5340  失败=0  超时=0  对端关闭=2974  速率=100/s
```

`失败=0`、`超时=0`，新连接一直建得上，但 `对端关闭` 跟着 `累计成功` 同步上涨，存活数被压在一个水位上不去。平均连接寿命约等于 `存活 ÷ 关闭速率`（这个例子约 24 秒）。

**本工具的 server 从不主动关闭健康的连接**，只在收到对端 FIN 或读写出错时才关闭。所以这些 FIN/RST 不是你的服务端程序发的，报告里会直接指出这一点：

```
  形态  : 踢旧建新 —— 新连接一直建得上, 但旧连接被对端关闭(FIN/RST) 362 条
          稳态水位 41 条(历史峰值 104), 平均每条连接活约 2 秒后被关掉
  注意  : 本工具的 server 不会主动关闭健康的连接, 所以这些 FIN/RST 大概率来自
          中间设备的会话回收, 或服务端的 accept 队列溢出 / 进程重启。
```

形态 B 下 `失败` 恒为 0，所以 `-G` 判定触顶看的是**存活数有没有创新高**，而不是有没有失败。

### 形态 C：悄悄掉线

`累计成功` 在涨，`存活` 缓慢下降，报告里的 `心跳发现失效` 变正。NAT/CGNAT 表满时的表现是**静默回收**，而不是 `connect` 失败：连接看起来还在，其实已经不通了，只有靠心跳才能发现。缩短心跳周期（`-B 5`）并延长观察时间（`-w 120`）可以确认。

> 降速后又能继续建连，说明刚才撞到的是 CPS 限制；降速后仍然失败，才是真正的容量上限。

### 失败归因对照表

| 主要失败类型                 | 判定                      | 处理                                 |
| ---------------------- | ----------------------- | ---------------------------------- |
| 超时（SYN 无响应）            | 上游静默丢 SYN（CGNAT / 网关限速） | 换一条链路对比验证                          |
| `Connection refused`   | 服务端 accept 队列溢出         | 服务端调大 `somaxconn` 和 backlog        |
| `Connection reset`     | 本机或服务端 `somaxconn` 过小   | `sysctl -w net.core.somaxconn=65535` |
| `Can't assign requested address` | 四元组 / 本地端口耗尽          | 加大 `-p` 端口范围，或用 `-b` 绑定更多源 IP；CPS 模式下用 `-L` |
| `Too many open files`  | 本机 fd 上限                | `ulimit -n 1048576`                |
| 成功率正常，p99 飙升           | 队列积压，已接近上限              | 把这个速率当作上限                          |
| 达成率低，延迟正常              | 客户端单线程发不出               | 加大 `-M` / `-I`，或多进程并行              |

### 服务端对拍：识别伪造的 FIN/RST

「客户端建连成功」不等于「服务端真的收到了」；同样，「客户端收到 FIN/RST」也不等于「服务端真的发了」。把服务端进度行的 `当前 / close累计` 和客户端对拍：

- **服务端 `close累计` ≈ 客户端 `对端关闭`，服务端 `当前` ≈ 客户端 `存活`**：关闭确实发生在服务端。检查 accept 队列溢出、`tcp_abort_on_overflow`、进程有没有被 OOM 杀掉。
- **服务端 `当前` 明显大于客户端 `存活`**（服务端以为连接还活着）：FIN/RST 是**链路中间设备伪造的**，基本可以确定是 CGNAT 会话回收或云厂商防护。

**最终结果以服务端的 `累计 accept` 为准**，两边对不上就说明有连接在中途被丢了。

服务端侧可以顺手检查：

```bash
sudo sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max
sudo dmesg | tail -50                     # conntrack table full / oom-kill
netstat -s | grep -iE "overflow|reset"    # accept 队列溢出
```

Windows 上用 `netstat -s -p tcp`，看 `Failed Connection Attempts` 和 `Reset Connections`。

### 链路瓶颈定位

如果目标是测**云主机服务端的并发容量**，却从**家宽**发起压测，那么家宽出口在 2000 条左右就会撞墙，服务端可能连 1% 的能力都没用到。**必须用同机房 / 同内网的另一台云主机当客户端**，才能测出服务端的真实容量。反过来，如果就是想测这条家宽链路的上限，那卡住的数值本身就是结论。

#### 是否在 CGNAT 之后

对比本机内网 IP 和公网出口 IP，更关键的是看 **traceroute 第 2 跳**：

```bash
ip -4 addr                          # 本机内网 IP（macOS: ipconfig getifaddr en0）
curl -s --max-time 8 ifconfig.me    # 公网出口 IP（先 env | grep -i proxy 确认没走代理）
traceroute -m 4 -w 1 -q 1 223.5.5.5
```

第 2 跳落在 `100.64.0.0/10`（RFC 6598 运营商级 NAT 专用地址段）就是 CGNAT。

> `curl` 看到的出口 IP 是公网地址，**并不能排除 CGNAT**，那可能只是 CGNAT 设备的公网侧，由很多用户共用。实测中 `111.27.69.229` 看起来是公网 IP，但 traceroute 第 2 跳是 `100.127.0.1`，实际处在 CGNAT 之后。

#### 路由器还是运营商：三步区分

本地路由器 NAT 表满和运营商 CGNAT 配额用满，现象几乎一样，都是静默丢 SYN。按成本从低到高排查：

| 步骤                   | 操作                         | 判定                                            |
| -------------------- | -------------------------- | --------------------------------------------- |
| ① 看路由器 NAT 会话数       | 测试进行时登录网关管理页，实时看会话数和 CPU    | 顶在 2048 / 4096 这类整数档、管理页卡顿 → **路由器瓶颈**        |
| ② 用 IPv6 直连重测        | 用支持 IPv6 的工具直连云主机的 IPv6 地址（本工具目前只支持 IPv4） | 轻松超过 2000 → **瓶颈在 IPv4 NAT 层**；仍然卡住 → 线路级配额或服务端 |
| ③ 光猫改桥接，本机 PPPoE 拨号  | 系统网络设置里添加 PPPoE，输入宽带账号     | 仍卡在同一数值 → **运营商限制**；上限大涨 → **路由器限制**          |

补充：让同一路由器下的**第二台设备同时压测**。两台合计仍是同一个总数，说明是全局表限制；各自都能到上限，说明限制是按每个内网 IP 计算的。

解决办法：向运营商申请公网 IPv4（家宽一般可以免费或低价开通），CGNAT 层就消失了，上限只取决于路由器；换路由器或刷 OpenWrt 调大 conntrack 可以继续往上走。

## 容量天花板与调优

真正的上限由下面几项中**最小**的那个决定：

| 天花板       | 计算 / 位置                       | 典型值                      |
| --------- | ----------------------------- | ------------------------ |
| 进程 fd     | `ulimit -n`                   | 默认 1024，需要调到 100 万以上     |
| 系统 fd     | `fs.file-max`、`fs.nr_open`    | 通常几百万                    |
| **四元组空间** | 源 IP 数 × 本地端口数 × 目标端口数         | 单源 IP、单目标端口约 6 万          |
| **内存**    | 连接数 × (收发缓冲 + 内核 sock 结构)     | 每条约 8 ~ 16 KB            |
| conntrack | `nf_conntrack_max`            | 默认常见 26 万左右，**最容易被忽略**    |
| accept 队列 | `somaxconn`                   | macOS 和部分 Linux 默认只有 128 |

客户端启动时会打印本机的 fd 上限、本地端口范围和四元组理论容量，目标连接数超过这些值时会直接告警。

### backlog 被静默截断

`listen(fd, 65535)` 会被内核截断到 `somaxconn`。macOS 默认只有 **128**，部分 Linux 发行版也一样。大并发建连时 accept 队列会溢出，表现为客户端报「建连成功」，服务端却并没有收到。服务端启动时会检查并告警，修复方法：

```bash
sudo sysctl -w net.core.somaxconn=65535     # Linux
sudo sysctl -w kern.ipc.somaxconn=65535     # macOS
```

### 内存估算

```
所需内存 ≈ 连接数 × (tcp_rmem + tcp_wmem + struct sock ≈ 1.5KB)
```

默认缓冲下每条连接约 8 ~ 16 KB，**100 万连接需要 8 ~ 16 GB 内存**。本工具把每条连接的 `SO_RCVBUF` / `SO_SNDBUF` 压到了 4 KB，`tune.sh` 也调小了 `tcp_rmem` / `tcp_wmem`，可以显著降低这个数字。

### 突破单 IP 约 6 万端口的限制

一个源 IP 连一个目标端口，最多用约 6 万个本地端口，这是硬限制。要测更高的并发：

```bash
# 方法一：服务端监听多个端口（最简单）
./server -p 8000-8031                                  # 32 个端口
./client -s 10.0.0.2 -p 8000-8031 -c 2000000 -r 200    # 容量 ≈ 6 万 × 32 ≈ 192 万

# 方法二：客户端绑定多个源 IP（这些 IP 要先配置在本机网卡上）
sudo ip addr add 10.0.0.5/24 dev eth0
sudo ip addr add 10.0.0.6/24 dev eth0
./client -s 10.0.0.2 -p 8000-8031 -b 10.0.0.5,10.0.0.6 -c 4000000 -r 200
```

### tune.sh / tune.ps1 做了什么

| 脚本         | 平台            | 主要改动                                                         | 持久性      |
| ---------- | ------------- | ------------------------------------------------------------ | -------- |
| `tune.sh`  | Linux         | fd 上限、本地端口 1024-65535、`somaxconn` / SYN 队列、收发缓冲、`tcp_mem`、TIME_WAIT、关闭 `syncookies`、放大 conntrack | 重启后失效    |
| `tune.sh`  | macOS         | `kern.maxfiles`、`somaxconn`、本地端口范围、keepalive、socket 缓冲上限    | 重启后失效    |
| `tune.ps1` | Windows       | 动态端口扩到 1025-65534，TIME_WAIT 从 120 秒降到 30 秒                  | **改注册表，重启后保留** |

- `TARGET=2000000 sudo ./tune.sh` 可以指定目标连接数（默认 110 万），用于计算 fd 上限。
- `tune.sh` 的改动需要持久化时，请自行写入 `/etc/sysctl.conf`。
- `tune.ps1` 用 `.\tune.ps1 -Revert` 恢复 Windows 默认值。
- 关闭 `syncookies` 是有意为之：它会掩盖真实的队列溢出，让「丢连接」看起来像「建连成功」。

### 原生版和 Linux / macOS 的差异

| 项目             | Linux / macOS           | Windows 原生版                                    |
| -------------- | ----------------------- | ---------------------------------------------- |
| 事件循环           | epoll / kqueue          | **select**                                     |
| 连接数上限          | 内存和 fd 决定（百万级）          | **`NB_WIN_FD_SETSIZE`，默认 8192**                |
| fd 上限          | `ulimit -n`             | 没有这个概念，启动时打印 select 后端的上限                      |
| TCP keepalive  | `TCP_KEEPIDLE`          | `SIO_KEEPALIVE_VALS`（`-k` / `-K` 同样有效）         |
| listen backlog | 受 `somaxconn` 限制，会告警    | Win8 起由系统动态管理，不告警                              |
| 端口复用           | `SO_REUSEADDR`          | 服务端改用 `SO_EXCLUSIVEADDRUSE`                   |
| 中断             | `SIGINT` / `SIGTERM`    | 控制台 Ctrl Handler，Ctrl-C 和关闭窗口都会正常输出报告          |
| 编译器            | cc / gcc / clang        | MinGW-w64、Clang；**MSVC 未适配**                   |

`select()` 每次调用都要线性扫描整个 fd 集合，是 O(n) 的。到几千条这一档时，客户端自己的 CPU 会先于链路成为瓶颈，**测出来的数字不代表真实容量**。目标在几千到一两万、只想快速验证时，原生版够用；要测真实上限请用 WSL2，或者调大 `NB_WIN_FD_SETSIZE` 重新编译（O(n) 开销也会同步放大）：

```bash
make windows WINCC="zig cc -target x86_64-windows-gnu" \
     CFLAGS="-O2 -Wall -Wextra -std=c11 -DNB_WIN_FD_SETSIZE=32768"
```

> **为什么不用 IOCP？** IOCP 是完成端口模型（proactor），和本项目 reactor 式的事件循环结构差别很大，接进来等于重写事件层。为了保持一份可读的跨平台代码，Windows 侧选了语义最接近的 select。

## 已知限制

- `-G` 自动停止需要先出现过异常信号（失败、对端关闭或心跳失效）。全程零异常、只是在慢慢建连的场景不会自动停止，请用 `-t` 设置总时限兜底。
- 存活数有正常抖动，`-G` 用「净增长 + 容忍阈值」判定，抖动很大时可能多等一个窗口。
- 客户端是单线程的，本机环境大约能发到每秒 3000 条，更高的 CPS 需要多进程并行。
- 心跳按 `-P` 限制每秒探测条数、分摊轮询。超过百万连接时一轮心跳会被拉长，形态 C 的发现会变慢。
- 只支持 IPv4。
- **Windows 原生版**：
  - select 后端是 O(n) 扫描，默认上限 8192 条，上万条时客户端 CPU 会先吃紧。
  - 已用 zig 交叉编译通过；select 后端已在 macOS 上用 `-DNB_FORCE_SELECT` 强制走同一套代码，跑通了建连、心跳、CPS 模式和踢旧建新判定。但 Winsock 相关部分（错误码翻译、`SIO_KEEPALIVE_VALS`、控制台 Ctrl Handler、`SO_EXCLUSIVEADDRUSE`）**还没有在真实 Windows 上跑过**，首次运行时请留意启动阶段的输出是否正常。
  - 四元组容量按 Windows 默认的 16384 个动态端口估算。跑过 `tune.ps1` 后端口范围已经扩大，但程序不会重新探测，估算值会偏保守。
  - MSVC（`cl.exe`）未适配（缺少 `getopt` 等 POSIX 接口），请用 MinGW-w64、Clang 或 WSL2。

## 注意事项

- **只对自己的机器做测试。** 对公网或他人的服务发起大量连接属于 DoS 行为。
- 测试结束后会留下大量 `TIME_WAIT`，这是正常现象。可以用 `ss -s`（Linux）、`netstat -an | grep -c TIME_WAIT`（macOS）或 `(netstat -an | Select-String TIME_WAIT).Count`（Windows）观察回收情况。
- `tune.sh` 的改动重启后失效；`tune.ps1` 改的是注册表，重启后仍然保留。

### 修改 Windows 相关代码前请先看

1. **`SOCKET` 是 typedef，不是宏。** 不要用 `#ifndef SOCKET` 判断平台。Winsock 把 `SOCKET` 定义为 `UINT_PTR`，`#ifndef` 会成立，`#define SOCKET int` 就会把真正的 64 位类型悄悄换成 int，表现为 `FD_SET` 报 `-Wsign-compare`。
2. **`getsockopt(SO_ERROR)` 返回的是 WSA 错误码**（如 10061），不是 errno。不翻译的话失败归因会全部落空，报告里只有一堆 `Unknown error`。统一用 `nb_so_error()` 翻译。
3. **不要用 `WSAPoll` 探测连接失败。** 微软已确认它在连接失败时不回报 `POLLERR`，会把「服务端没启动」误报成「超时」。请用 `select` 的写集合加异常集合。
4. `closesocket`、`ioctlsocket(FIONBIO)`、`SIO_KEEPALIVE_VALS`、`SO_EXCLUSIVEADDRUSE` 都已经在 `wincompat.h` 里封装好，新代码请直接复用，不要再手写 `#ifdef`。
5. **不要假设 Windows 有 6 万个本地端口**，默认动态端口只有 16384 个。
6. Windows 的 `fd_set` 是 SOCKET 数组而不是位图，`FD_SETSIZE` 限制的是**条数**，不是 fd 数值的大小。select 后端因此用 `(fd, mask)` 数组维护关注列表，不按 fd 数值建索引。
